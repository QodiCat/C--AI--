# 1. 我对“优雅代码”的理解

优雅的代码，不是“写得高级”，也不是“代码越短越好”。

我更倾向于这样定义：

> **优雅代码 = 让下一个接手的人，可以快速理解、放心修改，而且不容易改坏的代码。**

甚至可以再简单一点：

> **代码首先是写给人看的，其次才是给机器执行的。**

一段代码能运行，只解决了“今天”的问题；一段易维护的代码，要解决“半年以后还能不能改”的问题。

# 2. 优雅代码最重要的几个特征

## 2.1 一眼能看懂“这段代码想干什么”

例如：

```typescript
if (user.vip && order.amount > 1000 && !order.couponUsed) {
  price = price * 0.9;
}
```

能运行，但业务意图需要自己翻译。

可以改成：

```typescript
const isEligibleForVipDiscount =
  user.isVip &&
  order.amount > VIP_DISCOUNT_THRESHOLD &&
  !order.hasUsedCoupon;

if (isEligibleForVipDiscount) {
  price = applyVipDiscount(price);
}
```

后者代码变多了，但反而更容易理解。

所以：

> **优雅 ≠ 少写代码。**
>
> **优雅 = 少让别人动脑补全你的意图。**

---

## 2.2 一个函数只做一件事情

不太好的代码经常长这样：

```typescript
async function createOrder(data) {
  // 参数检查
  // 查询数据库
  // 计算价格
  // 判断优惠券
  // 创建订单
  // 扣库存
  // 调支付
  // 发短信
  // 发邮件
  // 写日志
}
```

这个函数很可能最后变成 300 行。

更好的方式：

```typescript
async function createOrder(command: CreateOrderCommand) {
  validateOrder(command);

  const products = await productRepository.findByIds(command.productIds);

  const pricing = calculateOrderPrice(products, command);

  const order = await orderRepository.create({
    ...command,
    pricing,
  });

  await inventoryService.reserve(order);
  await paymentService.createPayment(order);

  return order;
}
```

阅读的时候，你甚至不需要进入子函数，就知道整个业务流程：

```text
校验
↓
查商品
↓
计算价格
↓
创建订单
↓
锁库存
↓
创建支付
```

这就是很重要的一种代码美感：

> **代码结构本身就是业务流程图。**

# 3. 命名比注释更重要

## 3.1 不好的命名

```typescript
const a = getData();

const temp = a.filter(x => x.s === 1);

function handle(x) {
}
```

问题不是程序运行不了，而是两个月以后连自己都不知道是什么意思。

## 3.2 更好的命名

```typescript
const orders = getOrders();

const paidOrders = orders.filter(
  order => order.status === OrderStatus.PAID
);

function calculateRefundAmount(order: Order) {
}
```

好的命名最好能回答三个问题：

```text
它是什么？
它做什么？
它为什么存在？
```

所以一般不建议大量使用：

```text
data
info
obj
item
temp
res
result
handle
process
doSomething
```

除非上下文本身已经非常明确。

# 4. 不要滥用注释

很多人觉得：

> 注释多 = 代码规范。

其实未必。

例如：

```typescript
// 判断用户是不是VIP
if (user.isVip) {
}
```

这个注释基本没有任何价值。

更有价值的注释应该解释：

> **为什么这么写。**

例如：

```typescript
// 支付渠道最多允许查询最近 90 天的交易，
// 因此超过 90 天的退款必须走人工审核。
if (daysSincePayment > 90) {
  return requireManualReview();
}
```

代码告诉你 **What**。

注释最好告诉你 **Why**。

# 5. 少写嵌套代码

这是判断代码质量非常好用的指标。

例如：

```typescript
function pay(order) {
  if (order) {
    if (order.status === 'pending') {
      if (order.amount > 0) {
        if (order.user) {
          // payment
        }
      }
    }
  }
}
```

随着业务增加，很快就变成：

```text
if
  if
    if
      if
        if
```

维护起来非常痛苦。

可以使用 Early Return：

```typescript
function pay(order: Order) {
  if (!order) {
    throw new OrderNotFoundError();
  }

  if (order.status !== OrderStatus.PENDING) {
    throw new InvalidOrderStatusError();
  }

  if (order.amount <= 0) {
    throw new InvalidOrderAmountError();
  }

  if (!order.user) {
    throw new UserNotFoundError();
  }

  return paymentService.pay(order);
}
```

阅读路径会简单很多。

一个比较实用的原则：

> **尽量让正常业务路径保持在最左边。**

而不是一路向右缩进。

# 6. 少用“魔法值”

例如：

```typescript
if (user.level === 3) {
}

if (order.status === 2) {
}

if (amount > 10000) {
}
```

别人会问：

```text
3 是什么？
2 是什么？
10000 为什么？
```

应该改成：

```typescript
if (user.level === UserLevel.VIP) {
}

if (order.status === OrderStatus.PAID) {
}

if (amount > MANUAL_REVIEW_THRESHOLD) {
}
```

这样业务规则是显式的。

# 7. 业务规则不要散落在整个系统里

这个问题在真实项目里特别常见。

比如规定：

> 订单超过 1000 元，VIP 用户打九折。

千万不要变成：

```text
前端写一遍
订单接口写一遍
支付接口写一遍
后台管理写一遍
定时任务再写一遍
```

否则以后改成 95 折，你根本不知道应该改哪几个地方。

更好的方式是：

```typescript
class PricingService {
  calculate(order: Order, user: User): Money {
    ...
  }
}
```

所有价格计算统一走：

```typescript
pricingService.calculate(...)
```

这就是：

> **Single Source of Truth，单一事实来源。**

对于维护性而言，这是极其重要的原则。

# 8. 区分“业务逻辑”和“技术逻辑”

这是我认为中大型项目里最重要的一件事。

例如创建订单：

```typescript
async function createOrder(req, res) {
  const db = await mysql.connect();

  const user = await db.query(...);

  if (...) {
  }

  const products = await db.query(...);

  let price = 0;

  for (...) {
  }

  await redis.set(...);

  await axios.post(...);

  res.json(...);
}
```

这里混在一起的是：

```text
HTTP
数据库
Redis
业务规则
价格计算
支付接口
返回格式
```

非常难测，也非常难维护。

更合理的是：

```text
Controller
    ↓
Application Service
    ↓
Domain
    ↓
Repository / Infrastructure
```

例如：

```typescript
class OrderController {
  constructor(
    private readonly createOrderUseCase: CreateOrderUseCase
  ) {}

  async create(req: Request) {
    return this.createOrderUseCase.execute(req.body);
  }
}
```

业务：

```typescript
class CreateOrderUseCase {
  async execute(command: CreateOrderCommand) {
    const products = await this.productRepository.findByIds(
      command.productIds
    );

    const order = Order.create({
      userId: command.userId,
      products,
    });

    await this.orderRepository.save(order);

    return order;
  }
}
```

至于 MySQL 还是 MongoDB：

```typescript
class MySQLOrderRepository implements OrderRepository {
}
```

业务层根本不用知道。

这样未来数据库换了，核心业务逻辑几乎不动。

# 9. 模块之间要“低耦合，高内聚”

这句话很多人背过，但是在实际代码里很重要。

比如：

```text
userService
orderService
paymentService
productService
```

如果最后变成：

```text
userService 调 orderService
orderService 调 userService
paymentService 调 orderService
orderService 调 paymentService
productService 调 orderService
```

整个项目会形成蜘蛛网。

一个模块改一下，五个模块一起炸。

理想状态应该类似：

```text
Order
 ├── Pricing
 ├── Inventory
 └── Payment
```

模块内部高度相关：

> 高内聚。

模块外部通过明确接口交互：

> 低耦合。

# 10. 不要过度抽象

这是很多“追求优雅代码”的人最容易犯的问题。

例如本来：

```typescript
function getUser(id: string) {
  return db.user.findUnique({ where: { id } });
}
```

为了所谓设计模式搞成：

```text
AbstractDataSource
↓
BaseRepository
↓
GenericRepository
↓
UserRepositoryInterface
↓
UserRepositoryImpl
↓
UserDataAccessor
↓
UserDataService
```

最后查个 User 跳七个文件。

这种不是优雅，是：

> **抽象税。**

一个非常好的原则是：

> **不要为“可能发生”的未来提前设计大量抽象。**

也就是：

> YAGNI — You Aren't Gonna Need It.

只有当你真的发现：

```text
A、B、C 三个地方重复
```

再考虑抽象。

不要看到：

```text
A
```

就预测：

```text
以后说不定有 B、C、D、E……
```

然后造一个框架出来。

# 11. DRY 也不要走极端

DRY：

> Don't Repeat Yourself

是一个好原则，但很多人会误解成：

> 不能出现两段相似代码。

其实更准确的是：

> **同一个知识、同一个业务规则不要重复表达。**

例如：

```typescript
function calculateVipDiscount() {}
```

如果五个地方分别写一遍 VIP 规则，就是坏的重复。

但两个看起来类似、业务意义完全不同的逻辑：

```typescript
validateRegisterEmail()

validateBillingEmail()
```

即使当前代码一样，也不一定应该合并。

因为未来变化原因可能完全不同。

所以判断是否抽象，不是：

> 代码长得像不像。

而应该问：

> **它们是不是因为同一个原因发生变化？**

# 12. 错误也应该是业务的一部分

不推荐：

```typescript
throw new Error('error');
```

也不太推荐：

```typescript
return {
  code: 500,
  message: 'something wrong'
};
```

更推荐定义明确错误：

```typescript
class InsufficientInventoryError extends Error {}

class OrderAlreadyPaidError extends Error {}

class CouponExpiredError extends Error {}
```

然后：

```typescript
if (inventory < quantity) {
  throw new InsufficientInventoryError();
}
```

调用层很容易理解：

```typescript
try {
  await createOrder();
} catch (error) {
  if (error instanceof InsufficientInventoryError) {
    return conflict('库存不足');
  }
}
```

业务异常因此变得非常清晰。

# 13. 数据结构往往比算法更重要

例如不要到处传：

```typescript
{
  a: 1,
  b: 'abc',
  c: true
}
```

而是定义：

```typescript
interface CreateOrderCommand {
  userId: string;
  items: OrderItemInput[];
  couponId?: string;
}
```

返回：

```typescript
interface OrderSummary {
  orderId: string;
  totalAmount: number;
  status: OrderStatus;
}
```

很多代码质量问题，其实不是函数写得不好，而是：

> **数据模型没有设计清楚。**

一旦数据模型设计清晰，代码通常会自然变简单。

# 14. 最好的代码往往“不炫技”

例如这种：

```typescript
const result = arr
  .reduce((a, b) => ({
    ...a,
    [b.x]: [...(a[b.x] || []), b]
  }), {});
```

可能很聪明。

但是：

```typescript
const usersByDepartment = new Map<string, User[]>();

for (const user of users) {
  const departmentUsers =
    usersByDepartment.get(user.departmentId) ?? [];

  departmentUsers.push(user);

  usersByDepartment.set(
    user.departmentId,
    departmentUsers
  );
}
```

虽然更长，但可能更容易维护。

业务代码里，我通常更喜欢：

> **无聊的代码。**

因为“无聊”意味着：

```text
没有谜语
没有技巧
没有隐藏行为
没有过度抽象
```

看一遍就懂。

# 15. 一个非常重要的判断标准：能不能安全修改

假设产品经理说：

> 原来 VIP 满 1000 元九折，现在改成不同等级不同折扣。

如果你的代码需要：

```text
搜索 30 个文件
修改 15 个 if
祈祷没有漏掉
```

说明设计已经有问题。

理想情况应该是：

```typescript
class DiscountPolicy {

  getDiscount(user: User, order: Order): number {
    switch (user.level) {
      case UserLevel.GOLD:
        return 0.9;

      case UserLevel.SILVER:
        return 0.95;

      default:
        return 1;
    }
  }
}
```

变化被限制在一个小范围里。

所以我认为一个很核心的设计目标是：

> **让变化发生在局部。**

# 16. 我比较推荐的一套实际工程标准

如果你以后带团队开发，我建议要求大家至少做到：

| 维度  | 标准                    |
| --- | --------------------- |
| 命名  | 看名字基本知道用途             |
| 函数  | 尽可能只负责一个职责            |
| 文件  | 一个文件围绕一个核心概念          |
| 模块  | 明确业务边界                |
| 参数  | 尽量使用明确的数据结构           |
| 常量  | 禁止大量魔法数字/字符串          |
| 嵌套  | 优先 Early Return       |
| 异常  | 明确区分业务异常              |
| 重复  | 相同业务规则只存在一份           |
| 抽象  | 出现真实重复后再抽象            |
| 注释  | 解释 Why，而不是 What       |
| 依赖  | 核心业务不要直接依赖技术实现        |
| 测试  | 核心业务规则可独立测试           |
| 格式  | formatter / lint 自动统一 |
| API | 输入输出结构稳定明确            |

# 17. 一个我非常喜欢的代码结构

如果是你现在经常做的 Web / AI SaaS 项目，我会推荐类似：

```text
src/
├── modules/
│   ├── user/
│   │   ├── domain/
│   │   ├── application/
│   │   ├── infrastructure/
│   │   └── interface/
│   │
│   ├── order/
│   │   ├── domain/
│   │   ├── application/
│   │   ├── infrastructure/
│   │   └── interface/
│   │
│   └── payment/
│
├── shared/
│   ├── database/
│   ├── cache/
│   ├── logger/
│   ├── errors/
│   └── utils/
│
└── main.ts
```

而不是：

```text
controllers/
services/
models/
utils/
```

里面各塞几百个文件。

前者是：

> **按业务组织代码。**

后者往往是：

> **按技术类型组织代码。**

项目小的时候区别不明显，项目大了之后，按业务模块拆通常明显更容易维护。

# 18. 最后可以记住这 8 句话

如果让我把“优雅代码”浓缩成几个原则，就是：

1. **让代码表达业务意图，而不是实现细节。**
2. **一个函数尽量只做一件事。**
3. **好的命名可以消灭大量注释。**
4. **让正常路径保持简单，尽量减少嵌套。**
5. **同一个业务规则只能有一个事实来源。**
6. **不要为了未来可能出现的需求过度抽象。**
7. **让不同模块能够独立变化。**
8. **优雅代码最重要的不是好看，而是好改。**

如果一定要给“好代码”一个最终判断标准，我会用这句话：

> **当需求改变时，你能不能准确知道改哪里，而且只改很少的地方，并且有信心不会影响其他功能。**

这比代码行数、设计模式数量、用了多少高级语法，都更重要。
