# AI 穿搭建议原理分析

日期：2026-11-10。来源：用户要求“AI生成穿搭的建议 原理需要分析拆解”。本文区分代码现状与后续方案；不代表新推荐规则已实施或验收。

## 1. 当前建议如何产生

当前链路：前端提交定位与场景 → 后端查询高德天气 → 获取本人可穿衣物 → 调用 AI 提供方 → 返回候选与天气 → 用户保存或反馈。

| 环节 | 当前实现 | 边界 |
| --- | --- | --- |
| 天气与场景 | 定位查询城市、日期、天气、当前及日夜温度、风向风力，用户提供场景 | 天气失败会阻断生成；不是根据资料城市推测天气 |
| 衣物筛选 | 仅查询当前用户、正常管理且可穿的衣物 | 没有按温度、品类完整性或场景做生成前筛选 |
| Qwen 输入 | 单品 ID、名称、一级分类、主色、材质、季节、风格，以及上述环境信息 | 推荐调用不传图片；细分类、版型、图案、辅助色、场景标签、备注和身体数据未传入 |
| 组合与解释 | 提示词要求模型生成三套，每套至少两件，附名称、场景、风格、季节与理由 | 组合取舍来自模型已有知识与本次输入；项目没有独立知识库或评分函数 |
| Qwen 结果校验 | 三套数量、必填字段、每套至少两件、ID 属于输入衣橱、套内 ID 不重复 | 没有检验是否完整可穿、适温、配色合理或三套互有差异 |
| 保存与反馈 | 保存时复核本人单品可用性；喜欢/不喜欢写入任务记录 | 反馈未被下一次生成读取，不构成个性化学习 |
| 局部替换 | 找同一级分类中最近更新的另一件可穿衣物 | 不是重新计算整套搭配，未综合颜色、天气和风格 |

代码依据：`server/internal/modules/recommendation/routes.go`、`server/internal/modules/ai/provider.go`、`qwen.go`、`service.go`。

以上详细生成与校验行为属于 Qwen 路径。工程还支持外部 HTTP 提供方及显式 mock：HTTP 路径转发完整衣物模型，校验不等同于 Qwen；mock 只是取前几件并重复三套，不能作为真实推荐质量依据。本文未读取私密配置，不能据此判断线上正在使用哪种提供方。

## 2. “建议理由”应怎样理解

当前 `reason` 与单品组合由模型在同一次请求中输出。它是模型对组合的文字说明，没有独立规则执行记录或知识来源支持，不能当作系统已验证过的结论。例如“适合降雨”并不意味着后端验证了鞋的防水性。

推荐质量可以拆成五个问题：

1. 能不能穿：单品可用、上下装或连衣裙等主体结构成立，不能用两个配饰充当完整搭配。
2. 适不适合当天：当前与日夜温度、风雨、活动场景和可脱穿层次是否匹配。
3. 视觉是否协调：颜色关系、轮廓、材质与图案是否形成可解释的组合。
4. 是否符合个人选择：风格偏好、舒适度、禁忌与真实反馈是否参与判断。
5. 是否有选择价值：三套在单品或穿法上有差异，并明确适用条件与取舍。

现阶段代码主要保证单品来源与输出结构；其余大部分依赖模型判断。“有理由文字”与“搭配质量得到验证”应分开验收。

## 3. 主要缺口

- 输入不够完整：系统已有一些衣物属性，但 Qwen 未使用；无法仅凭身高围度推断个人审美或可靠的穿着效果。
- 知识不可追溯：没有可维护的穿搭规则、适用条件、例外和出处。
- 缺少业务校验：合法 ID 不代表完整搭配；三套可以完全重复。
- 解释缺少证据约束：未要求每条理由绑定具体衣物属性、天气字段或知识条目。
- 反馈没有闭环：记录喜欢/不喜欢后，下一次生成仍不使用这些记录。
- 天气提示词残留旧字段：Qwen 提示词仍提“体感温度、风速”，实际高德上下文提供风向和风力等级；应在后续实现中对齐，避免模型误解。

## 4. 建议的后续原理

建议链路：结构化输入 → 可用性与必要条件筛选 → 检索适用知识 → 生成候选 → 业务校验与排序 → 选择有差异的方案 → 输出有依据的解释 → 收集反馈。

### 知识库的作用

知识库提供可审查的搭配依据，不是把所有穿搭文章拼进提示词。初期可用结构化条目与标签筛选；规模和检索需求明确后，再评估是否需要向量检索，不必一开始引入新基础设施。

每条知识建议包含：编号、主题、适用条件、建议动作、例外、不确定性、来源及审核状态。主题可覆盖色彩、比例与轮廓、材质、图案、场景、气候与叠穿。尚未搜集和核验外部资料，本次不将任何具体穿搭经验定为权威规则。

例如，一个待审核的“日夜温差下的可脱穿叠穿”条目，应写清何种天气与活动适用、需要哪些已有衣物、哪些信息缺失时不能下结论；不应直接把某个温度写成所有人的统一舒适阈值。

### 规则、模型与解释的分工

| 能力 | 建议职责 |
| --- | --- |
| 后端规则 | 保证本人衣物、可穿状态、ID 有效、组合结构、用户明确禁忌等必要条件 |
| 知识检索 | 按天气、场景、衣物属性与明确偏好提供相关条目，排除不适用内容 |
| 大模型 | 在约束内提出组合与穿法，结合知识给出说明，标明信息不足 |
| 排序与去重 | 按适温、场景、协调性、偏好与方案差异比较候选；权重需用样例验证，不预设为科学评分 |
| 解释输出 | 指出使用了哪些单品事实、天气事实和知识编号，说明取舍；后端校验引用是否真实存在 |
| 反馈 | 关联具体方案、单品与上下文，区分不喜欢颜色、版型或场景不符等原因，再逐步调整排序 |

硬约束与审美偏好要分开。衣物不足或信息不足时应明确缺口，不能为了返回三套而虚构单品。是否允许部分搭配、是否必须包含鞋履、允许怎样的重复程度，需要先确认产品口径；现有“至少两件、允许重复组合”的规则暂不改变。

## 5. 建议实施顺序与验收

1. 先补输入与校验：对齐天气提示词，选择必要衣物字段，建立统一的提供方结果校验；用缺少主体单品、重复方案、失效 ID 等用例验证。
2. 建立小规模人工审核知识集：先选常见天气与场景，记录来源、适用条件及例外；验证检索命中和不适用条目排除。
3. 接入生成与解释：对照当前方案评估完整性、适温性、差异性和解释依据；不能只看 JSON 返回成功。
4. 再接个人反馈：使用可追溯的方案标识与上下文，验证反馈是否影响后续候选；用户身体数据仅在用途明确、信息足够时使用。

质量评估应固定一组衣橱与天气样例，结合自动规则检查和人工判断，记录失败原因；未完成真实模型对照评估前，不宣称推荐质量已提升。

本次完成代码静态分析与方案拆解，没有修改运行行为、调用真实 AI、部署服务或开展客户验收。后续待确认：知识来源与审核方式、完整搭配标准、个人化范围及质量验收样例。
